# ТЗ: проверка проектов на утёкшие ключи и токены

Повод — на karatsapov.ru токен Telegram-бота для заявок лежал в клиентском
JavaScript (`lead-config.js`) и отдавался всем посетителям. Бота переименовали
посторонние. Это не единичная ошибка, а типовая: так же утекают ключи карт,
почтовых сервисов, CRM и аналитики.

Задача — пройти остальные проекты по одной процедуре и закрыть то же самое.

## 2. Что именно ищем

### Критично — ротировать немедленно

| Что | Как выглядит | Чем грозит |
| --- | --- | --- |
| Токен Telegram-бота | `1234567890:AAE…` (8–10 цифр, двоеточие, 35 символов) | чтение всех заявок, рассылка от вашего имени, переименование бота |
| Приватный ключ | `-----BEGIN … PRIVATE KEY-----` | доступ к серверу или подпись от вашего имени |
| Пароль от БД или SMTP | `mysql://user:pass@`, `password=`, `SMTP_PASS` | доступ к данным, рассылка спама с вашего домена |
| Ключ облака | `AKIA…` (AWS), `AIza…` (Google), `y0_…` / `AQAA…` (Яндекс) | счёт за чужие ресурсы |
| Токен CRM или платёжки | `vk1.a.…`, вебхуки amoCRM, ключи ЮKassa | доступ к сделкам и деньгам |
| Файл `.env` в репозитории | — | обычно всё сразу |

### Не секрет, ротировать не нужно

Чтобы не тратить время: идентификатор счётчика Яндекс.Метрики, `measurement
id` Google Analytics, публичный ключ карт для фронтенда (но у него должна быть
ограничена привязка к домену), pixel id VK. Это публичные по назначению.

## 3. Где искать — шесть мест

Проверять надо все шесть. Чистый репозиторий ничего не значит, если секрет
отдаётся живым сайтом, и наоборот.

### 3.1 Живой сайт — главное место

Именно здесь утечка работает прямо сейчас.

```bash
SITE=https://example.ru

# какие скрипты подключает главная
curl -s "$SITE" | grep -oE '(src|href)="[^"]+\.(js|json|txt)"' | sort -u

# скачать каждый и просмотреть (подставьте пути из вывода выше)
curl -s "$SITE/app.js" | grep -nE '[0-9]{8,10}:AA[A-Za-z0-9_-]{33}|AIza[0-9A-Za-z_-]{35}|AKIA[0-9A-Z]{16}|-----BEGIN|password|secret|token|api[_-]?key'
```

Проверьте и служебные адреса — они открываются чаще, чем кажется:

```bash
for p in .env .git/config .git/HEAD config.php backup.zip dump.sql \
         wp-config.php.bak .DS_Store composer.lock package.json; do
  printf '%-18s ' "$p"
  curl -s -o /dev/null -w '%{http_code}\n' "$SITE/$p"
done
```

**Любой ответ 200 на `.env`, `.git/*` или `*.sql` — критическая находка.**
Открытый `/.git/` позволяет скачать весь исходный код вместе с историей.

### 3.2 Сборка

Секрет может отсутствовать в исходниках, но подставляться при сборке.

```bash
npm run build 2>/dev/null || true
grep -rInE '[0-9]{8,10}:AA[A-Za-z0-9_-]{33}|AIza[0-9A-Za-z_-]{35}|-----BEGIN' dist/ build/ public/ 2>/dev/null
```

Отдельно проверьте **source maps** (`*.js.map`): в них попадает исходный код
со всеми комментариями и иногда с ключами, которые в минифицированной версии
не видны.

### 3.3 Исходники

```bash
grep -rInE '[0-9]{8,10}:AA[A-Za-z0-9_-]{33}|AIza[0-9A-Za-z_-]{35}|AKIA[0-9A-Z]{16}|vk1\.a\.|y0_[A-Za-z0-9_-]{20,}|-----BEGIN [A-Z ]*PRIVATE KEY' . \
  --exclude-dir=node_modules --exclude-dir=.git --exclude-dir=dist
```

Затем глазами по именам файлов: `config.js`, `settings.js`, `constants.js`,
`.env*`, `credentials*`, `*secret*`, `*token*`.

### 3.4 История git

Секрет, удалённый из текущей версии, остаётся в истории навсегда.

```bash
# по всей истории разом
git grep -InE '[0-9]{8,10}:AA[A-Za-z0-9_-]{33}|AIza[0-9A-Za-z_-]{35}|-----BEGIN' $(git rev-list --all)

# какие файлы вообще когда-либо назывались подозрительно
git log --all --diff-filter=A --name-only --format= | sort -u | grep -iE '\.env|secret|credential|token|key'
```

Если в окружении есть `gitleaks` или `trufflehog` — прогнать ими, они точнее:

```bash
gitleaks detect --source . --no-banner
```

### 3.5 Публичность репозитория

```bash
gh api /repos/ВЛАДЕЛЕЦ/РЕПО --jq '{private, visibility}'
```

Публичный репозиторий означает, что всё из пункта 3.4 доступно любому и,
скорее всего, уже проиндексировано ботами, которые сканируют GitHub на
предмет ключей — они находят новый токен за минуты.

Там же включите защиту на будущее: **Settings → Code security → Secret
scanning** и **Push protection**. Для публичных репозиториев это бесплатно и
блокирует пуш с секретом ещё до отправки.

### 3.6 Сторонние сервисы

Куда ещё вы могли вставить ключ руками: Яндекс.Метрика (цели с параметрами),
Google Tag Manager (пользовательские теги), Тильда (блок с HTML-кодом),
опубликованные Google-таблицы, которые используются как база, публичные гисты,
посты и скриншоты в чатах.

## 4. Отдельно: проверка Telegram-ботов

Для каждого бота из списка в разделе 1.

1. Откройте [@BotFather](https://t.me/BotFather) → `/mybots` → бот.
2. Сверьте **имя, аватар и описание** с тем, что вы ставили. Изменились —
   токеном пользовались посторонние: эти поля меняются методом `setMyName`
   по одному токену, без доступа к вашему аккаунту.
3. Проверьте, не стоит ли чужой вебхук:

```bash
curl -s "https://api.telegram.org/bot<ТОКЕН>/getWebhookInfo"
```

Непустой `url`, которого вы не ставили, — бот уводит заявки на чужой сервер.

4. При любом сомнении — **Revoke current token** в BotFather. Это единственное
   действие, которое реально закрывает доступ; удаление секрета из кода его не
   закрывает.

## 5. Что делать с находкой

Порядок именно такой. Сначала ротация, потом уборка — наоборот бессмысленно.

| Тип | Как ротировать |
| --- | --- |
| Telegram-бот | BotFather → `/mybots` → API Token → Revoke current token |
| Яндекс OAuth, API карт | Кабинет разработчика → удалить ключ, выпустить новый, ограничить по домену |
| VK | vk.com/apps?act=manage → пересоздать сервисный ключ |
| Google | console.cloud.google.com → Credentials → Regenerate, поставить ограничение по HTTP-referrer |
| SMTP, БД | сменить пароль, проверить журнал входов за последний месяц |
| Приватный ключ SSH | выпустить новый, старый убрать из `authorized_keys` на всех серверах |

После ротации:

1. Убрать секрет из кода и сборки.
2. Проверить журналы на предмет чужой активности за время утечки.
3. Переписать на серверную схему (раздел 6).
4. Историю git чистить не обязательно — после ротации старый ключ бесполезен.
   Если всё же нужно: `git filter-repo` и force-push, с пониманием, что
   форки и кэш GitHub могут сохранить старое.

**Если утекали персональные данные клиентов** (имена, телефоны, почты из
заявок) — оценить объём и период. По 152-ФЗ утечка подлежит уведомлению
Роскомнадзора в течение 24 часов с момента обнаружения.

---

## 6. Как должно быть устроено

Правило одно: **в браузер нельзя отдавать ничего, что даёт доступ.** Любой
секрет в клиентском коде публичен по определению — минификация, обфускация и
`base64` ничего не меняют, это пять секунд работы.

Правильная схема приёма заявок:

```
форма → ваш эндпоинт на сервере → Telegram / CRM / почта
                ↑
        токен лежит здесь и только здесь
```

Требования к эндпоинту:

- секреты в переменных окружения или в файле с правами `600`, не в репозитории;
- в репозитории — только `.env.example` с пустыми значениями;
- ограничение частоты запросов: не больше 5 заявок с адреса в минуту, иначе
  форму используют как спам-рассылку;
- защита от ботов — honeypot-поле или капча;
- первичная запись персональных данных на российском сервере (152-ФЗ);
- запасной путь на случай недоступности: если отправка не прошла, форма
  открывает мессенджер с заполненным текстом, чтобы заявка не потерялась.

заявок.
