# Переезд с GitHub Pages на свой сервер

## Почему переезжаем

Сайт открывался не у всех. Симптом: «Не удаётся получить доступ к сайту»,
код **ERR_CONNECTION_CLOSED**, при этом с мобильного интернета всё в порядке.

Что проверено и исправно:

- DNS отвечает одинаково с четырёх резолверов, включая яндексовский;
- CAA-записей нет, выпуску сертификата ничто не мешает;
- ветка `gh-pages` актуальная, файл `CNAME` на месте;
- сборка и деплой зелёные;
- до адресов GitHub Pages сеть достаёт — по `dkaratsapov-web.github.io`
  отдаётся стандартная страница GitHub.

Диагноз. `ERR_CONNECTION_CLOSED` означает, что соединение установилось и
было оборвано — как правило, на TLS-рукопожатии, где браузер открытым
текстом передаёт имя сайта. Адрес пропускается, имя — нет. Ни кэш, ни
смена DNS, ни перевыпуск сертификата на это не влияют.

Лечится уходом с адресов GitHub Pages на собственный сервер.

## Перед началом: какой из серверов

В аккаунте два сервера. Деплой из GitHub Actions уже настроен и ходит на
один из них — тот, чей адрес лежит в секрете `VPS_HOST`.

Проще всего взять именно его: тогда ничего менять не придётся. Проверить,
на какой сервер уже приезжает сайт, можно так — зайти по SSH на каждый и
посмотреть:

```bash
ls /var/www/landing
```

Где лежит `index.html` и каталоги `about`, `blog`, `keysy` — тот и нужен.

Если сайт решено вешать на **другой** сервер, поменяйте секреты в
GitHub: Settings → Secrets and variables → Actions → `VPS_HOST` (адрес),
`VPS_USER`, `VPS_SSH_KEY`. После этого запустите воркфлоу **Deploy to VPS**
вручную и дождитесь зелёной галочки.

## Шаг 1. Подготовить сервер

Один раз, от пользователя с sudo:

```bash
curl -fsSL https://raw.githubusercontent.com/dkaratsapov-web/landing/main/deploy/setup-vps.sh | sudo bash
```

Скрипт поставит nginx и certbot, создаст каталоги, положит конфиг сайта,
проверит синтаксис и перезапустит nginx. В конце он напечатает внешний
адрес сервера — он понадобится на следующем шаге.

Скрипт можно запускать повторно, ничего не сломается.

**Сертификат на этом шаге не выпускается.** Так и надо: Let's Encrypt
проверяет домен, обращаясь к серверу по имени, а домен пока указывает на
GitHub. Сначала DNS, потом сертификат.

## Шаг 2. Проверить сервер, пока домен ещё не переключен

Полезная проверка: сайт можно открыть по новому адресу до переезда,
подставив имя вручную.

```bash
curl -I --resolve karatsapov.ru:80:АДРЕС_СЕРВЕРА http://karatsapov.ru/
```

Ожидаем `HTTP/1.1 200 OK`. Если `403` — файлы сайта не приехали, запустите
воркфлоу **Deploy to VPS**. Если `404` — проверьте, что в
`/var/www/landing` лежит `index.html`.

## Шаг 3. Понизить TTL

В панели reg.ru у записей домена выставить TTL **300 секунд** и сохранить.

Лучше сделать это за час-два до самого переключения: старое значение уже
разошлось по кэшам, и понижение начнёт действовать не сразу.

## Шаг 4. Переключить DNS

В reg.ru:

| Запись | Было | Стало |
| --- | --- | --- |
| `A` для `@` | 185.199.108.153 и ещё три | адрес сервера |
| `www` | CNAME на `dkaratsapov-web.github.io` | `A` на адрес сервера |

Четыре старых адреса GitHub Pages удалить, CNAME для `www` — тоже.

Дождаться, пока разойдётся:

```bash
nslookup karatsapov.ru 8.8.8.8
```

Обычно 5–15 минут.

## Шаг 5. Выпустить сертификат

```bash
sudo certbot --nginx -d karatsapov.ru -d www.karatsapov.ru
```

Certbot допишет в конфиг блок с TLS, создаст вспомогательные файлы и
настроит автоматическое продление. На вопрос про редирект отвечайте
**2 (Redirect)** — он сам добавит переход с http на https.

Затем:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

## Шаг 6. Проверить

```bash
curl -I http://karatsapov.ru          # 301 на https
curl -I https://karatsapov.ru         # 200
curl -I https://www.karatsapov.ru     # 301 на karatsapov.ru
curl -I https://karatsapov.ru/about/  # 200
curl -I https://karatsapov.ru/net-takoj-stranicy/   # 404 и своя страница
```

И открыть сайт в браузере на том канале, где он раньше не открывался.

## Шаг 7. Проверить автопродление

Самый пропускаемый шаг, а цена ошибки — сайт ляжет через три месяца.

```bash
sudo certbot renew --dry-run
```

Должно закончиться без ошибок.

## После переезда

**Через несколько дней спокойной работы** добавить в блок `server` с
портом 443 строку и перезагрузить nginx:

```nginx
add_header Strict-Transport-Security "max-age=15768000" always;
```

Раньше не стоит: заголовок запрещает браузеру полгода ходить на сайт по
http, и отменить это у тех, кто уже его получил, нельзя.

**Деплой на GitHub Pages пока не выключать.** Пусть полежит запасной
копией пару недель: если с сервером что-то пойдёт не так, вернуть домен
обратно будет делом одной записи в DNS.

**Поисковикам сообщать не нужно** — домен не меняется, меняется только
сервер. Канонические адреса и карта сайта не затрагиваются.

**Проверить формы.** Заявки уходят в WhatsApp (токен Telegram в
`lead-config.js` намеренно пустой, он был публичным). Отправьте тестовую
заявку и убедитесь, что открывается вкладка с готовым текстом.

## Если что-то пошло не так

**`nginx -t` ругается на сертификат** — значит certbot ещё не отработал.
Конфиг из репозитория содержит только http, блок с TLS добавляет certbot.

**Certbot не может проверить домен** — DNS ещё не разошёлся либо порт 80
закрыт. Проверьте, что домен уже указывает на сервер, и что фаервол
пропускает 80 и 443:

```bash
sudo ufw allow 'Nginx Full'
```

**Сайт отдаёт 403** — файлов нет в `/var/www/landing`. Запустите воркфлоу
**Deploy to VPS**.

**Сайт отдаёт «Welcome to nginx»** — остался включённым стандартный сайт:

```bash
sudo rm -f /etc/nginx/sites-enabled/default && sudo systemctl reload nginx
```

**После переезда сайт всё равно не открывается** — тогда фильтруется само
доменное имя, а не адрес. Проверяется так:

```bash
curl -I --resolve karatsapov.ru:443:АДРЕС_СЕРВЕРА https://karatsapov.ru
```

Если с сервера отвечает, а из дома нет — вопрос к домену, и решается он
только сменой доменного имени. Случай редкий, до него, скорее всего, не
дойдёт.
