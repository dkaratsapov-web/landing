# Переезд с GitHub Pages на свой VPS

## Почему переезжаем

Сайт открывался не у всех. Симптом: браузер показывает «Не удаётся получить
доступ к сайту», код **ERR_CONNECTION_CLOSED**, при этом с мобильного
интернета всё в порядке.

Что при этом проверено и исправно:

- DNS отвечает одинаково с четырёх резолверов, включая яндексовский;
- CAA-записей нет, выпуску сертификата ничто не мешает;
- ветка `gh-pages` актуальная, файл `CNAME` на месте;
- сборка и деплой зелёные;
- до самих адресов GitHub Pages сеть достаёт — по адресу
  `dkaratsapov-web.github.io` отдаётся стандартная страница GitHub.

Из этого следует диагноз. `ERR_CONNECTION_CLOSED` означает, что соединение
установилось и было оборвано — как правило, на TLS-рукопожатии, где браузер
открытым текстом передаёт имя сайта. Адрес пропускается, имя — нет. Ни кэш,
ни смена DNS, ни перевыпуск сертификата на это не влияют: фильтрация идёт
уровнем ниже.

Единственное решение — уйти с адресов GitHub Pages на собственный сервер со
своим адресом. Деплой туда уже настроен и отрабатывает на каждый пуш
(`.github/workflows/deploy-vps.yml`, rsync в `/var/www/landing/`), то есть
свежая копия сайта на сервере уже лежит.

## Порядок

Шаги 1–3 выполняются заранее и ничего не ломают: домен в этот момент
по-прежнему смотрит на Pages, сайт работает как работал.

### 1. Понизить TTL у записи (за час-два до переезда)

В панели reg.ru у A-записи `karatsapov.ru` выставить TTL **300 секунд**.

Это делается заранее, потому что старое значение TTL уже разошлось по
кэшам: понизив его за пять минут до переезда, вы ничего не выиграете.

### 2. Подготовить сервер

```bash
sudo apt update
sudo apt install -y nginx certbot python3-certbot-nginx

# Каталог для проверки домена. Именно отдельный, не внутри /var/www/landing:
# туда ходит rsync --delete и снесёт проверочный файл при следующем деплое.
sudo mkdir -p /var/www/acme
sudo chown -R www-data:www-data /var/www/acme

# Каталог сайта — туда уже кладёт файлы деплой из GitHub Actions.
sudo mkdir -p /var/www/landing
ls /var/www/landing        # должен быть index.html и остальное
```

Если каталог пуст — запустите воркфлоу `Deploy to VPS` вручную через
Actions → Run workflow и дождитесь зелёной галочки.

### 3. Положить конфиг

Файл `deploy/nginx-karatsapov.conf` из этого репозитория:

```bash
sudo cp nginx-karatsapov.conf /etc/nginx/sites-available/karatsapov.ru
sudo ln -sf /etc/nginx/sites-available/karatsapov.ru /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
```

Проверить синтаксис **пока не получится** — в конфиге есть пути к
сертификату, которого ещё нет. Это нормально, сертификат появится на шаге 5.

### 4. Переключить DNS

В reg.ru заменить A-запись `karatsapov.ru` на IP вашего сервера. Удалить
четыре адреса GitHub Pages (185.199.108.153, 185.199.109.153,
185.199.110.153, 185.199.111.153).

Запись `www` сделать такой же A-записью на тот же IP (сейчас это CNAME на
`dkaratsapov-web.github.io` — его нужно убрать).

Дальше подождать, пока изменения разойдутся. Проверять так:

```bash
nslookup karatsapov.ru 8.8.8.8
```

Когда в ответе будет ваш IP — идти дальше. Обычно это 5–15 минут.

### 5. Выпустить сертификат

```bash
sudo certbot --nginx -d karatsapov.ru -d www.karatsapov.ru
```

Certbot сам подставит пути к сертификату в конфиг, создаст
`options-ssl-nginx.conf` и `ssl-dhparams.pem` и настроит автоматическое
продление. На вопрос про редирект отвечайте, что редирект уже настроен
вручную (вариант «No redirect»), — иначе certbot допишет свой и получится
два.

Затем:

```bash
sudo nginx -t          # теперь проверка синтаксиса пройдёт
sudo systemctl reload nginx
```

### 6. Проверить

```bash
curl -I http://karatsapov.ru        # должен быть 301 на https
curl -I https://karatsapov.ru       # должен быть 200
curl -I https://www.karatsapov.ru   # должен быть 301 на karatsapov.ru
curl -I https://karatsapov.ru/about/          # 200
curl -I https://karatsapov.ru/net-takoj-stranicy/   # 404 и своя страница
```

И открыть сайт в браузере на том канале, где он раньше не открывался.

### 7. Проверить автопродление

Самый пропускаемый шаг, и цена ошибки — сайт ляжет через три месяца.

```bash
sudo certbot renew --dry-run
```

Должно закончиться без ошибок.

## После переезда

**Дать сайту несколько дней спокойной работы,** потом раскомментировать
строку с `Strict-Transport-Security` в конфиге и перезагрузить nginx.
Раньше не стоит: заголовок запрещает браузеру полгода ходить на сайт по
http, и отменить это у тех, кто уже его получил, нельзя.

**Не выключать деплой на GitHub Pages сразу.** Пусть полежит запасной копией
пару недель — на случай, если с сервером что-то пойдёт не так, вернуть
домен обратно будет делом одной записи в DNS.

**Сообщить о переезде поисковикам не нужно** — домен не меняется, меняется
только сервер. Ни канонические адреса, ни карта сайта не затрагиваются.

**Проверить формы.** Заявки уходят в WhatsApp (в `lead-config.js` токен
Telegram намеренно пустой). Отправьте тестовую заявку и убедитесь, что
открывается вкладка с готовым текстом.

## Что делать, если после переезда сайт всё равно не открывается

Тогда фильтруется не адрес и не имя, а что-то ещё — например, сам домен
попал в списки. Проверить это можно так: открыть на сервере тот же сайт по
IP-адресу с подстановкой имени.

```bash
curl -I --resolve karatsapov.ru:443:ВАШ_IP https://karatsapov.ru
```

Если с сервера отвечает, а из дома нет — вопрос к домену, и решается он
только сменой доменного имени. Но это редкий случай, и до него, скорее
всего, не дойдёт: смена адреса лечит подавляющее большинство таких историй.
